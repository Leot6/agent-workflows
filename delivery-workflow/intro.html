delivery-workflow, at a glance

Drives small-to-medium implementation work from a ready plan to reviewed, committed code — unattended by default, through an independent quality gate. This page orients; the authority is the tree itself: the flow table is config/stages.tsv, the contracts are runtime-docs/, the map is README.md. Where this page and those disagree, those win.

The flow

plan-validate→ split⇄split-check→ spec→precheck⇄revise→impl→postcheck⇄fix→turnover × N slices → close-out
  • topic → slice → stage. A plan is cut into function-shaped slices; each slice advances through stages; the ferry (a table-driven loop) moves every handoff.
  • Outlined chips are contract-cold sessions — round-1 reviews and spec start with a fresh context, because independence is bought, not hoped for. Other stages reuse a warm session: authoring context is the value.
  • Two loops, two convergence guards. precheck ⇄ revise and postcheck ⇄ fix iterate until the reviews stop finding substantive defects; split ⇄ split-check iterates until the cut of the plan settles.
  • A stage completes only by emitting a record into the store (nonce-authenticated) — never prose. What the ferry reads is mechanical fields only.

Who does the work

ferry — the loop

A plain process, table-driven: select the next stage, compose the prompt from template + manifest, spawn or reuse a session, wait for the record, route on its fields. It never reads artifact prose and never reasons.

author — writes

Specs the slice, drives impl, writes conformance and turnover. Its sub-agent, the implementer, executes one commit-unit per dispatch and reports; the diff, not the report, is the authority.

reviewer — the floor

Independent lineage, re-derives every load-bearing claim first-hand. Precheck gates the spec; postcheck gates the landed commits.

pilot — optional middleware

Routes and relays (rulings, relaunch, notifications); never decides substance. A dead pilot degrades to the owner-paged baseline — full-auto does not depend on it.

owner — the decisions

Class-U questions, pushes, disagreements that do not converge. Everything else is machinery or agents.

When it stops

Full-auto halts for exactly four things, and every park names itself — reason, detail, and the captured screen where relevant:

haltmeaningthe answer
class_uan owner decision is owedlaunch.sh rule — the only resume path
blockedthe implementer cannot proceedread the evidence; a ruling authorises the widening
disagreementa review loop is not convergingthe owner rules continue / split / redesign
push_gatework landed; push is owedthe owner pushes — the workflow never does

The per-reason playbook (all twenty of them) is runtime-docs/operations.md §3; launch.sh status --halt prints the full question set, untruncated.

What holds it together

one table, one derivation

Every stage's owed outputs are declared in stages.tsv and derived by one code path — emit's gate, the ferry's advance and park-on-miss all ask the same list. A backstop cannot share an item with the failure it catches, because there is only one list.

one atomic store

Plain files under .runtime/state/, checksummed, one writer class per surface. Fault ≠ absent: a corrupt read is never silently zero. The state is regenerable and never hand-edited.

capabilities, never names

A backend CLI is a declaration file (screen signatures, capabilities); the ferry switches on declared capabilities only. A renamed CLI can never silently change behaviour.

judgment to the cheapest instrument

Mechanical claims are gated at emit time; author-fixable defects close in the author's own refine loop; only judgment-class claims reach the independent reviewer; only the owner decides. Each party is disturbed as little as it can be.
