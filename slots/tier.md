## The harm it would prevent

planning's no-exemptions rulings (A§13: baseline-check mandatory for every
topic, no size threshold) price in a real floor: pin + card + check +
design/grill + per-round lenses, regardless of topic size. That is correct
as a ruling — the exemption judgment is itself the judgment that fails
silently. The unpriced half: for a small topic the floor can exceed the
work's value by an order of magnitude, and nothing in the protocol can see
that, so the owner pays it in silence.

## The design (criteria draft — mechanical, not judgment)

A tier is COMPUTED at round 0 from three mechanical quantities, never
declared by the author:

| tier | topic statement | card rows after first pass | distinct touched files |
|---|---|---|---|
| light | ≤ ~1 paragraph, single ask | ≤ 10 | ≤ 5 |
| standard | (default) | — | — |
| full | any foundations flag from the grill, or pin spans >2 repos | — | — |

Tier scales, never skips: light scales ROUND_MAX (5→3), the ordinary-round
lens set (arch+red → arch), brief-field minimum (six fields → four: 来龙去脉 /
推荐怎么做 / 完整形象示例 / 代价与最强反方), refine depth (3 passes → 1 + on-dirty).
Every gate stays: card, baseline-check, executor, convergence checklist —
depth scales, the floor does not move.

Mid-topic re-tier rides the two EXISTING event triggers in protocol §2
(scope/foundations pivot ⇒ immediate cold restart + re-derive) — no new
judgment surface.

## External anchor

RADAR-style risk-proportional review depth (review effort scaled to the
expected loss of what escapes) is the industry shape; the measured anchors
inside this repo (NEEDS-MF rate ~7× above ~600 lines/commit; PBR lens yield
by class, rationale §5) are the calibration data the build will use.

## Why not built now

Zero light-tier live topics exist: the thresholds above are drafts with no
data behind them (admission (c)). The first topic whose retro records the
floor cost as the dominant line item is the demonstrated need; this slot's
criteria then get calibrated from that topic's ledger before the mechanism
lands as a planning-tree protocol edit (single-purpose commit, validation-debt
row until a second topic exercises it).
